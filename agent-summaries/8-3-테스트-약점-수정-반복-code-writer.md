# score.test.ts 약점 수정 (code-writer)

수정 파일: packages/core/src/score.test.ts (score.ts는 수정하지 않음, 커밋 없음)

## 변경 내용
1. 14장 검사와 isAgari 경로를 분리했다.
   - "14장이 아니면 에러": 1장 손패와 13장 손패(`123m 456m 789m 12p 77s 99s`)를 사용하고 메시지 "14장"을 단언한다.
   - "14장이지만 화료형이 아니면 에러": `123m 456m 12p 45p 77s 99s`(14장, 1m 포함)를 사용하고 메시지 "화료 형태"를 단언한다.
2. "치토이츠와 표준형이 모두 가능하면 더 높은 쪽을 채택" 테스트의 단언을 정확한 값으로 교체했다.
3. winningTile이 손패에 없으면 throw하는 테스트를 추가했다. `PINFU_HAND`에 9s를 지정하고 메시지 "winningTile"을 단언한다.
4. 옵션 검증 테스트를 `const opts: ScoreOptions = {}; opts[key] = bad;` 형태로 변경했다. 0 케이스도 같은 방식이다.

## 항목 2 재계산 근거 (참고 예상치와 다름)
손패는 `11m 22m 33m 44m 55m 66m 77m`, 당첨패 1m, 리치, 론이다.
- 치토이츠 후보: 리치 1판 + 치토이츠 2판 = 3판, 25부. 기본점은 25*2^5 = 800이고 론은 3200이다.
- 표준형 후보: 123m x2 + 456m x2 + 77m 분해에서 1m은 23m 양면이라 핑후가 성립한다. 역은 리치 + 핑후 + 이페이코로 3판이다. 론 30부이므로 기본점은 30*2^5 = 960이고 론은 3900이다. 44m을 대자로 하는 123 123 567 567 분해도 같은 결과다.
- 960이 800보다 높으므로 score.ts는 표준형을 채택한다. 예상치 [riichi, chiitoitsu]는 표준형 후보를 과소평가한 값이었다.
- 이 엔진에는 청일색과 량페이코가 없다. 그래서 위 계산이 이 구현의 실제 동작이다.
- 테스트 기대값은 yaku id 정렬 결과 [iipeikou, pinfu, riichi], han 3, fu 30, basePoints 960, payment ron 3900이다.
- score.ts와 어긋난 부분은 없다. 테스트를 구현에 억지로 맞춘 것이 아니라 손계산으로 확인한 값이다.

## 실행 여부
`npm test --workspace=@mahjong/core`와 `npm run build --workspace=@mahjong/core`는 **미실행**이다. Bash 도구가 안전 분류기 오류(no verdict)로 두 번 막혔고 우회하지 않았다. 통과 여부는 확인되지 않았다.
